1. Aim

To build and review a Flask application that provides workshop resources through separate participant and administrator portals, applying practical secure-development controls to authentication, access control, input validation, database operations, and logging.

2. Application Overview

Participants can register, sign in, browse the workshop timetable, and search learning resources. Administrators use an environment-provisioned account to manage resources and review reports and audit activity. Role checks are enforced on protected server routes.

3. Tools and Technologies

  • Python and Flask with separate route blueprints.
  • SQLite and SQLAlchemy ORM.
  • Flask-JWT-Extended for access and refresh tokens.
  • Flask-WTF for CSRF protection; Flask-Limiter for login rate limits.
  • Werkzeug password hashing and Jinja template autoescaping.
  • Pytest for automated verification.

4. Security Implementation

  • Passwords are stored as hashes and are not logged in plain text.
  • JWTs are stored in HttpOnly cookies. Access-token lifetime is 15 minutes by default; refresh-token lifetime is one day.
  • Participant and administrator roles are checked on protected routes; participant tokens cannot access administrator routes.
  • CSRF tokens protect state-changing form and AJAX requests. Login endpoints are rate-limited.
  • Server-side validation constrains required values, lengths, allowed options, and URL schemes.
  • SQLAlchemy ORM queries use bound parameters; templates escape user-provided text.
  • Security headers and audit events are configured. Secrets and the local database are excluded from Git.
  • The participant login portal shows a timeout message after five minutes without activity. There is no inactivity timer or inactivity-based logout after login.
  • The development server binds to localhost. Production requires HTTPS and strong environment secrets.

5. Results

Authentication tests after the timeout update: 13 passed. The preceding full suite reported 32 passed before that update. The rate limiter currently uses in-memory storage, so a persistent shared backend is needed for multi-process production hosting.

6. Conclusion

The project demonstrates how authentication, server-side role checks, safe database access, CSRF protection, validation, and careful logging can be combined in a Flask application. It also shows that browser interface behavior and server authorization must be handled separately. Production readiness would require deployment-grade hosting, HTTPS, managed secrets, and persistent rate-limit storage.

Appendix D — Security Review Checklist

  • Only synthetic or authorized data is used.
  • Inputs are checked for type, length, allowed values, and missing values.
  • Database queries use parameters rather than string concatenation.
  • Passwords are not stored or logged in plain text; prototype credentials are for local educational use.
  • Secrets are not hard-coded or committed to version control.
  • User-facing error messages do not expose stack traces or sensitive paths.
  • State-changing actions use appropriate request methods and CSRF protection.
  • Logs record useful events while avoiding unnecessary personal or secret data.
  • Resource file access uses an allowlist; request size is limited and missing resources return an error page.
  • The application binds to localhost during development unless deployment is authorized.
  • Dependencies and setup instructions are documented.
  • Known limitations and future improvements are stated honestly.
